## Minimum runtime identity

The existing code calls S3 GetObject and conditional PutObject with SHA-256 verification and AES256 encryption. Runtime needs s3:GetObject and s3:PutObject only under the dedicated bucket's fdep-demo/* namespace. s3:ListBucket on that dedicated bucket supports distinguishing missing objects from access denial. Keep its current whole-dedicated-bucket ListBucket scope unless live missing-object behavior proves a prefix restriction works. No DeleteObject, bucket configuration, IAM, KMS customer-key, multipart, Snowflake AWS integration or general administrator access is needed. Teardown deletion belongs to the separate administrator session. The Snowflake load command also uses this S3 client to verify/read transferred objects.

The six-resource configuration creates an unattached managed IAM policy. It creates no runtime identity and no attachment. Attaching it to the current AdministratorAccess role would not reduce that role's privileges. Its saved trust policy permits only account-access.amazonaws.com to AssumeRole/SetContext, so direct self-assumption with a narrowing session policy is not supported by that trust. AWS-managed project controls protect roles under /managed/ from trust and permission modification. Do not modify the existing role. [Project controls](https://docs.aws.amazon.com/accounts/latest/reference/scps-and-rcps-for-projects.html)

The smallest proposed extension is **one custom IAM role outside /managed/**, such as /fdep/FdepTransferRuntime, plus **one attachment** of the existing transfer policy. Its trust should name only the existing managed project role ARN in this account, with no wildcard account trust. The existing browser session would be the source for an assume-role CLI profile; the SDK would receive temporary credentials for the scoped role. Use at most a one-hour chained session. MFA is handled by the source login; do not assume an IAM-user MFA context key is propagated by project login. [AssumeRole semantics](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)

This is a conditional design: published controls do not establish an account-wide ban on custom non-managed roles, but actual CreateRole, AttachRolePolicy and AssumeRole authorization is unverified. A read-only simulator can help but cannot guarantee a successful write. Before authorizing IAM changes, review the exact trust/policy and account restrictions. This extension would yield **eight resources**, requiring a new reviewed plan; the existing six-resource plan is not a complete least-privilege runtime deployment. It has not been edited or applied. No IAM users, keys, Identity Center instance or external identity provider are proposed.
