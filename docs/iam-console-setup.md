## If console access is supported

1. Select **Provide user access to the AWS Management Console**, then the IAM-user choice if AWS offers a choice between user types. Set a unique password locally and store it in your password manager. Because the same person is setting their final password, an initial forced password reset is unnecessary; do not add a password-management policy just for that step. Never send the password or download/share a credentials CSV.
2. On Permissions choose **Attach policies directly**. Attach only the AWS-managed **SignInLocalDevelopmentAccess** policy. Review the exact name, not AdministratorAccess, PowerUserAccess or ReadOnlyAccess. Create the user after reviewing its name and absence of access keys. [Managed policy](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/SignInLocalDevelopmentAccess.html)
3. In Users, fdep-operator, Permissions, choose **Add permissions → Create inline policy**. Select JSON and paste the full contents of `infrastructure/iam-plan-inspection.json`. Use policy name **FdepPlanInspection**. Review and create it. It permits inspecting only this user's own identity, attached/inline policies, MFA and access-key metadata, plus the login policy document. It grants no resource-write actions or S3 data reads.
4. Still administering the user, open **Security credentials → Multi-factor authentication → Assign MFA device**. Name it fdep-operator-mfa. Register your passkey/security key or authenticator app yourself. Keep QR seeds and one-time codes private. Confirm a device is assigned. The administrator registers it, so no self-service MFA write policy is required.
5. Confirm **Access keys = 0**. Record the IAM sign-in URL locally. Open a separate browser profile/private window and sign in as fdep-operator with its password and MFA. Check the displayed identity. Root remains only for account administration; don't choose root in the CLI browser flow.

The policy deliberately omits S3 permissions: with no existing Terraform state, this configuration's new-resource plan uses identity validation and local evaluation, and does not need to read existing objects or create a bucket. If Terraform requests additional access, inspect the specific failure before extending permissions. A successful plan does not prove that future deployment writes are allowed. Unexpected console panels may show AccessDenied because this is a restricted planning identity.
